每日新闻推送系统　云端架构设计与落地方案

编制日期：二〇二六年十一月十一日
适用前提：本地电脑不常开机，全部逻辑必须跑在云端，零常驻进程、零本地守护
调研基准：二〇二六年十一月，渠道配额与云免费额度均以各平台官网最新说明为准


【壹】结论先行

■ 主选方案
　云端定时：GitHub Actions 定时工作流（公开仓库）
　消息主通道：企业微信群机器人 Webhook，经微信插件直达个人微信
　消息副通道：QQ 官方机器人群聊主动消息（建一个只有自己的群）
　消息备份道：Server酱 或 PushPlus，兼作故障告警
　状态存储：仓库内 state.json（轻量）或云 KV（进阶）
　可复用底座：sansan0／TrendRadar（GPL-3.0）

■ 一句话运行机制
　每天北京时间七点三十分，GitHub 分配一台临时虚拟机，拉起脚本，抓取四类新闻源，
　做规范化、去重、分级与摘要，合并成一条简报，调用 Webhook 发到微信与 QQ，
　把已推 ID 与失败队列写回仓库后，虚拟机立即销毁。电脑关机完全不影响。

■ 为什么不选本地常驻
　无服务器、无 crontab、无需开机、无需公网 IP、无需备案域名；
　免费额度下每天一次的任务成本为零；密钥由云端 Secrets 托管，不落本地磁盘。


【贰】整体架构设计

■ 第一层　定时触发层
　○ 组件：GitHub Actions schedule 触发器（备选：腾讯云 SCF 定时触发器／阿里云 FC 定时触发器／Cloudflare Workers Cron）
　○ 职责：按 Cron 唤醒一次无状态执行环境，注入 Secrets，超时后回收
　○ 关键：计算器时区统一为 UTC（GitHub Actions），北京时间七点三十分写作 30 23 * * *

■ 第二层　采集层
　○ 时政：新华网、人民网、央广网、政府网政策发布
　○ 财经：财联社电报、界面新闻、第一财经、证券时报
　○ 科技：36氪、澎湃科技、极客公园、TechNode
　○ AI：机器之心、量子位、arXiv 摘要、官方模型发布博客
　○ 个人相关小事：个人关键词订阅（所在城市、行业、任职机构、关注公司、考试报名、补贴申报、天气预警、交通调整）
　○ 源形式：优先 RSS；无 RSS 的站点用 DIYgod／RSSHub 转成 RSS；热榜类可用 imsyy／DailyHotApi

■ 第三层　处理层
　○ 规范化：统一标题、时间、来源、链接，去除跟踪参数
　○ 去重：URL 级 → 事件级 → 推送级三层
　○ 分级：重大事件（即时插播）／常规要闻（进日报）／个人小事（只进日报，不即时打扰）
　○ 摘要：可选调用大模型（如 DeepSeek，OpenAI SDK 兼容）做归纳，只输出摘要与原链接，不转载全文
　○ 排版：一份 Markdown 简报，四个栏目 + 【与你相关】板块 + 源健康提示

■ 第四层　状态层
　○ 已推 ID 表：幂等键 + 时间戳，TTL 七天
　○ 待补队列：推送失败的内容，下次运行合并补发
　○ 日计数器：频率控制与静默时段的依据
　○ 载体：GitHub Actions 版写回仓库 state.json；云函数版用云 KV／对象存储／轻量数据库

■ 第五层　推送层
　○ 企业微信群机器人 → 个人微信（主）
　○ QQ 官方机器人群聊 → 手机 QQ（副）
　○ Server酱／PushPlus／邮件／ntfy（备份与告警）
　○ 通道适配器统一接口，任一通道失败自动切换

■ 横向贯穿
　○ 密钥托管、失败重试、心跳监控、运行日志、账单告警


【叁】运行机制与定时触发方式

■ 主选：GitHub Actions
　○ 机制：仓库 .github／workflows 下的 YAML 定义 schedule；触发时 GitHub 分配一台全新 Ubuntu Runner（四核十六吉内存），装好 Python，执行脚本，结束即销毁
　○ 定时：POSIX 五字段 Cron，仅 UTC；最小间隔五分钟
　○ 免费额度：公开仓库标准 Runner 免费；私有仓库 GitHub Free 每月二千分钟
　○ 已知限制（重要）
　　● 调度尽力而为，实测常见延迟五到三十分钟，高峰期可能更久；避开整点，用 23:30 而非 0:00
　　● 仓库连续六十天无任何活动，定时工作流会被自动禁用；机器人自身回写 state.json 的提交可续命
　　● 工作流文件必须在默认分支才会注册定时
　　● 官方不鼓励把 Actions 当作通用算力农场；每天一次小规模采集属于合理使用
　　● 公开仓库日志与产物公开，任何密钥都必须放 Settings → Secrets and variables → Actions
　○ 状态持久化：脚本结束时 git commit 并 push state.json，提交信息带 [skip ci] 防止再次触发工作流形成循环

■ 备选一：腾讯云 SCF 或阿里云 FC 云函数（推荐给"要准时、要国内网络"的场景）
　○ 机制：上传一个 Python 函数包，配置定时触发器（Timer），平台按 Cron 拉起实例，按实际执行时长计费，运行完释放
　○ 定时：控制台配置 Cron，支持秒级七字段表达式；时区以控制台所选地域／时区设置为准，务必先跑一次验证
　○ 优势：定时精度明显高于 GitHub Actions；国内源访问快；与微信生态同厂；可配异步重试与死信队列；超时可设六十到一百二十秒
　○ 免费额度：两家均有每月免费调用与资源额度，但二〇二六年政策多次调整（部分资料显示新用户试用三个月，之后有低价基础套餐）。每天一次的任务即使计费通常也在每月几角到几元，部署前请以官网计费页为准并设置账单告警
　○ 注意：依赖需一并打包或用依赖层；冷启动；函数默认超时较短需手动调大；部分境外源在国内地域访问不通

■ 备选二：Cloudflare Workers Cron Triggers
　○ 免费版每账号五个 Cron 触发器、每日十万次请求；UTC 定时；KV／D1 可做状态存储
　○ 硬伤：免费版每次执行仅十毫秒 CPU 时间，解析多份 RSS、跑相似度计算容易超限；国内访问部分源不稳定
　○ 定位：适合极轻量的转发与兜底，不适合作为主采集引擎

■ 备选三：Vercel Cron Jobs
　○ Hobby 版每天最多触发一次，且只在指定小时窗口内近似执行，UTC 定时，无自动重试，可能重复投递
　○ 定位：只适合"一天一次、时间不敏感"的极简版，且必须自己做幂等

■ 不推荐：云服务器 CVM／轻量应用服务器
　○ 需要自己维护系统、cron、安全组、续费，与"零运维、免费"目标相悖；仅在需要长期 WebSocket 连接时才有必要


【肆】消息推送渠道与实现思路

■ 结论：微信个人号没有官方开放的个人消息 API，所有"推到微信"的合规路径都是绕道服务号／企业微信／QQ 官方机器人。切勿使用模拟登录、协议号、Hook 类方案。

■ 通道一　企业微信群机器人 → 个人微信（主推）
　○ 实现：注册企业微信（个人可注册，无需认证付费）→ 建一个只有自己的群 → 添加群机器人 → 复制 Webhook URL → 在微信中绑定企业微信插件，消息即可出现在个人微信
　○ 调用：POST Webhook，msgtype 用 markdown（富文本）或 text（纯文本，兼容性更好，会自动去除 Markdown 语法）
　○ 配额：约二十条每分钟；无每日条数硬限；无需实名认证；零成本
　○ 注意：消息正文有字节上限，长简报需分段或截断；Webhook URL 等同于密码，必须放 Secrets
　○ 适配性：TrendRadar 原生支持，Secret 名为 WEWORK_WEBHOOK_URL，配合 WEWORK_MSG_TYPE=text 可直推个人微信

■ 通道二　QQ 官方机器人（副通道）
　○ 依据：QQ 开放平台 bot.qq.com 官方 API v2，二〇二六年已打通单聊、群聊与频道，群聊主动消息已开放
　○ 实现路径
　　● 在 QQ 开放平台创建机器人，取 AppID 与 AppSecret（Secret 只显示一次，丢失只能重置）
　　● 开发设置中开启「群聊消息」权限，机器人状态需为「已上线」，开发中状态无法调用 API
　　● 建一个只有自己的 QQ 群，把机器人拉进群，在群设置中打开「机器人主动在群聊内发言」
　　● 首次通过事件回调取得 group_openid（不是群号），一次性获取后存进 Secrets，之后无需长连接
　　● 用 AppID + AppSecret 换取 access_token（官方建议缓存约七千二百秒），再 POST 到 api.bot.qq.com／v2／groups／{group_openid}／messages
　○ 配额：Bot 维度未认证约三十条每分钟、认证约六十条每分钟；单群二十条每分钟、每群每天一千条
　○ 关键选择：走群聊而不是私聊。私聊主动消息受互动召回机制限制（用户需先与机器人对话，且仅有当天、一至三天、三至七天、七至三十天四个周期各一条），无法稳定做每日推送
　○ SDK 说明：官方 tencent-connect／botpy（MIT）最后提交于二〇二四年九月，已停更；但 API v2 文档二〇二六年仍在更新，建议直接调 REST，不要依赖 SDK
　○ 风险提示：NapCat／Lagrange／OneBot 等第三方协议端属模拟登录，违反平台条款且有封号风险，本方案不采用

■ 通道三　Server酱／PushPlus／WxPusher（备份与告警）
　○ Server酱（sct.ftqq.com）：微信扫码即得 SendKey，一次 HTTP 请求一条消息；新版走企业微信通道；免费版每日五条，会员约三十九元每年、每日可达一千条
　○ PushPlus（pushplus.plus）：免费版每日约二百条，需实名认证（身份证与小额认证费）；支持微信公众号、邮件等多通道
　○ WxPusher：扫码门槛低、配额宽松，但收消息体验依赖其客户端／公众号配置，部署前请以官网当前说明为准
　○ 定位：每日一条简报完全在免费额度内；更适合作为主通道故障时的备份与"系统挂了"的告警通道

■ 推送适配器设计
　○ 统一接口 send(title, content, level) → 依次尝试主通道、副通道、备份通道
　○ 每个通道独立记录成功／失败与剩余配额
　○ 重大事件可多通道并发，日常简报只走主通道，避免同一条消息在微信和 QQ 重复打扰


【伍】可复用开源方案（许可、维护状态、适配性）

■ 一　sansan0／TrendRadar　【首选，直接可落地】
　○ 许可：GPL-3.0
　○ 规模与维护：约六万三千星、二万四千余 Fork，最后提交二〇二六年十一月五日，活跃度极高
　○ 能力：聚合三十余个平台热榜 + RSS 订阅；关键词筛选（普通词、+必须词、!排除词、@数量上限、正则）；AI 筛选／翻译／分析简报；三种推送模式（当日汇总、当前榜单、增量监控）；原生支持 GitHub Actions 与 Docker；推送渠道含企业微信、飞书、钉钉、Telegram、邮件、ntfy、Bark、Slack、通用 Webhook；带 MCP 支持
　○ 适配性：与需求重合度最高，且"增量监控只推新增、保证零重复"直接解决去重问题；三种推送模式直接解决频率控制问题；关键词语法直接解决"个人相关小事"问题
　○ 注意：GPL-3.0 具传染性，若基于它二次开发并对外分发／提供网络服务需评估开源义务；个人自用无碍。项目迭代快，Fork 后定期同步上游，不要直接改主干逻辑
　○ 部署要点：用 Use this template 创建自己的仓库（不建议普通 Fork）；在 Settings → Secrets 添加 WEWORK_WEBHOOK_URL；编辑 config／config.yaml、config／frequency_words.txt、config／ai_analysis_prompt.txt；在 Actions 手动 Run workflow 验证；cron 写在 .github／workflows／crawler.yml

■ 二　newsnext／newsnow（原 ourongxing／newsnow，已迁至组织）　【数据源与阅读页】
　○ 许可：MIT
　○ 维护：约二万二千星，最后提交二〇二六年十一月九日，活跃
　○ 能力：实时与热门新闻的优雅聚合阅读，TypeScript，可部署 Cloudflare Workers／Vercel
　○ 适配性：适合作为"新闻源与前端展示层"；本身不含定时推送逻辑，需要自己在外层接采集与推送
　○ 注意：仓库地址已变更，老教程里的 ourongxing／newsnow 会失效

■ 三　DIYgod／RSSHub　【源扩展基础设施】
　○ 许可：AGPL-3.0
　○ 维护：约四万七千星，二〇二六年十一月十一日仍有提交，极活跃
　○ 能力：把没有 RSS 的网站、公众号、榜单转成标准 RSS
　○ 适配性：补齐"政策公告、地方发布、行业站点"这类个人相关小事的长尾数据源
　○ 注意：AGPL-3.0 对网络服务同样有开源义务，若将来做对外服务须合规评估；建议自建实例并加缓存，不要压公共实例（易限流、易被封）

■ 四　imsyy／DailyHotApi　【轻量补充源】
　○ 许可：MIT
　○ 维护：约四千一百星，最后提交二〇二六年三月十一日，距今约八个月，维护明显放缓
　○ 能力：今日热榜聚合 API，支持 RSS 模式与 Vercel 部署
　○ 适配性：可作为热榜补充，但源规则随目标站点改版易失效；只做锦上添花，不做主源

　○ 许可：MIT
　○ 维护：约一千七百六十星，最后提交二〇二四年七月三十日，已停滞两年多

　○ 适配性：接口与微信插件策略可能已变化，仅作理解通道原理用；直接复用企业微信群机器人 Webhook 更简单可靠

■ 六　tencent-connect／botpy　【QQ 通道参考】

　○ 适配性：适合读源码理解鉴权流程；生产建议按官方文档直接调 REST API

■ 组合建议
　○ 想最快见到效果：只用 TrendRadar（模板 + GitHub Actions + 企业微信机器人），一小时内可跑通
　○ 想长期可控：以 TrendRadar 的数据源与关键词思路为参考，自研精简版主脚本，RSS 用 RSSHub 补齐，状态层与重试自己掌握
　○ 涉及商用或对外发布：优先选 MIT 项目（newsnow、DailyHotApi），避开 GPL-3.0 与 AGPL-3.0 的传染性风险


【陆】所需组件与关键依赖

■ 云端账号与权限
　○ GitHub 账号（公开仓库）、企业微信组织（个人可建）、QQ 开放平台机器人（可选）、大模型 API Key（可选，如 DeepSeek）
　○ 云函数方案另需：腾讯云或阿里云实名账号、函数服务与对象存储／KV 权限、账单告警

■ 运行时与依赖（Python 版）
　○ Python 3.12 或 3.13（用户本机为 3.13.12；云函数运行时支持列表需在控制台确认）
　○ feedparser：RSS／Atom 解析
　○ requests 或 httpx：HTTP 请求
　○ PyYAML：读取 config.yaml
　○ zoneinfo 或 pytz：UTC 与北京时间换算
　○ tenacity：指数退避重试（也可手写）
　○ openai：调用 DeepSeek 等兼容接口做摘要（可选）
　○ datasketch 或 simhash：标题相似度去重（可选，小规模用内置 difflib 即可）
　○ 云函数版额外：依赖打包／层、Serverless Framework 或厂商 CLI

■ 配置文件清单
　○ config／config.yaml：源清单、栏目权重、个人关键词、重大事件关键词、推送策略、去重 TTL、每栏上限、AI 开关与模型
　○ .github／workflows／daily.yml：Cron、运行环境、Secrets 注入、超时、回写 state.json
　○ state.json：已推 ID、日计数器、待补队列、源健康分
　○ Secrets：见【柒】


【柒】配置方式

■ GitHub Secrets（名称严格一致，不要自创）
　○ WEWORK_WEBHOOK_URL　　企业微信群机器人 Webhook
　○ WEWORK_MSG_TYPE　　　 text 或 markdown（推个人微信建议 text）
　○ SERVERCHAN_SENDKEY　　备份通道（可选）
　○ PUSHPLUS_TOKEN　　　　备份通道（可选）
　○ QQ_APP_ID　　　　　　 QQ 机器人（可选）
　○ QQ_APP_SECRET　　　　 QQ 机器人（可选）
　○ QQ_GROUP_OPENID　　　 目标群 OpenID（可选）
　○ DEEPSEEK_API_KEY　　　AI 摘要（可选）
　○ HEARTBEAT_URL　　　　 心跳监控地址（可选）
　注意：Secret 保存后不可再查看，只能覆盖；一个 Name 对应一个 Secret；严禁写进代码或打印到日志。

■ 定时配置
　○ 北京时间 07:30 → GitHub Actions（UTC）：30 23 * * *（即前一日 UTC 二十三点三十分）
　○ 建议避开整点与 UTC 0 点高峰；如需晚间晚报可加第二个 cron，或改为单次运行内生成两份
　○ 云函数 Cron 多为七字段（秒 分 时 日 月 周 年），例如北京时间每天 07:30 写作 0 30 7 * * * *，务必先在控制台手动触发验证时区

■ 内容策略配置
　○ 每日一条汇总简报：四栏目各三到五条 + 【与你相关】零到三条 + 源健康提示
　○ 重大事件即时插播：全天上限一到二条，且仅在白天时段
　○ 静默时段：23:00 至 07:00 只入队不推送
　○ 个人关键词示例：南宁、数字经济、地方政府投资、投标、专项债、PB-ROE、掘金量化、报名截止、补贴申报、台风预警
　○ AI 摘要：可关闭；开启时要求模型只归纳、不编造，且每条保留原标题与原链接，末尾标注"摘要由模型生成，以原文为准"


【捌】部署步骤与运行注意事项

■ 部署（主选方案，约一小时）
　一、用 TrendRadar 的 Use this template 建自己的仓库，或直接采用随附的精简骨架
　二、企业微信建群、加机器人、复制 Webhook；微信侧绑定企业微信插件，先手动发一条测试消息
　三、在仓库 Settings → Secrets and variables → Actions 逐条添加密钥
　四、编辑 config.yaml 与 frequency_words.txt，填四个栏目的源与个人关键词
　五、Actions 页手动 Run workflow，确认手机收到简报，再交给定时任务
　六、配置心跳监控（Healthchecks.io 或同类），告警通道选与主通道不同的那条
　七、一周后检查 Actions 运行日志、state.json 增长、是否有重复推送

■ 运行注意事项（易踩坑）
　○ 工作流 YAML 必须在默认分支；公开仓库的定时最稳，私有仓库有分钟数与闲置限制
　○ 仓库六十天无活动会停掉定时；机器人自身回写提交可续命，也可每两月手动触发一次
　○ 回写 state.json 的提交信息必须带 [skip ci]，否则可能自我触发形成循环
　○ 单任务单写入：若同时开多个定时任务，回写仓库会冲突，需改云 KV 的原子操作或加锁
　○ GitHub Actions 的 cron 不准时，只承诺"当天送到"，别承诺"七点三十整送到"；要准时改用云函数
　○ 国内云函数访问 Google News RSS 等境外源可能不通；境外源请放在 GitHub Actions 的境外 Runner，国内源用云函数
　○ Google News RSS 的官方声明是"仅供个人 feed reader 非商业使用"，且链接为跳转编码、仅含标题，商用前需替换
　○ 消息正文有字节上限，长简报要分段；企业微信 markdown 与 text 的渲染不同，推个人微信优先 text
　○ QQ 侧：机器人须「已上线」、群聊权限已开、主动发言开关已开；access_token 需缓存；group_openid 不是群号
　○ 免费额度政策会变：不要绑定可无限扣款的支付方式，务必设置账单与用量告警
　○ 合规：只推标题、摘要与原链接，不全文转载；遵守目标站点 robots 与使用条款；控制抓取频率并设合理 User-Agent
　○ 密钥轮换：Server酱 SendKey、QQ AppSecret、企业微信 Webhook 泄露后立即重置，并同步更新 Secrets


【玖】关键问题处理方向

■ 一　消息频率控制
　○ 结构控制：默认"一天一条汇总"，重大事件即时插播设全天硬上限（一到二条），个人小事只进日报不即时打扰
　○ 配额表（部署前以官网复核）
　　● 企业微信群机器人：约二十条每分钟
　　● Server酱 免费版：每日五条；会员每日可达一千条
　　● PushPlus 免费版：每日约二百条
　　● QQ 群聊：单群二十条每分钟、每群每天一千条
　○ 令牌桶 + 日计数器：存状态层，超限自动合并到下一条；静默时段只入队
　○ 分级规则：重大政策、市场异动、重大模型发布、重大安全事件判为重大；其余按栏目权重排序截断
　○ 反打扰：同一事件即使多源命中，也只推一次；同一栏目设置每期条数上限

■ 二　重复推送去重
　○ 三层去重
　　● 源级：URL 规范化，去掉 utm 系列与其他跟踪参数、去掉锚点、跟随重定向取最终地址、统一大小写
　　● 事件级：标题归一化（去标点、去媒体前缀、繁简统一）后计算 SimHash 或 difflib 相似度，跨源同题合并为一条并标注多个来源
　　● 推送级：幂等键 = hash(规范化 URL 或事件簇 ID + 日期)，写入 state.json／KV，TTL 七天
　○ 幂等与投递语义：云平台多为"至少一次"投递，可能重复触发；因此必须先查幂等键，推送成功后再标记已推
　○ 失败补偿：采用"先占位、后确认"或"失败回滚占位"，避免推送失败后被误标为已推而永久丢消息
　○ 现成实现：TrendRadar 的「增量监控」模式只推新增内容，宣称零重复；「当日汇总」模式适合做每日一条

■ 三　数据源可靠性
　○ 冗余：每个栏目至少两个独立源，主源失败自动降级到备源，避免单点
　○ 超时与礼貌抓取：单次五到十秒超时、合理 User-Agent、条件请求（ETag／Last-Modified）、失败有限重试，不高频轮询
　○ 缓存快照：保留上一次成功结果，某源本次全失败时用快照兜底并在简报中标注"缓存内容"
　○ 源健康分：连续 N 次失败自动摘除并在简报末尾提示"某源暂不可用"，恢复后自动加回
　○ 时间校验：只收近二十四到四十八小时的条目，防止源返回陈旧缓存或批量回填旧闻
　○ 长尾源：地方公告、行业站点用自建 RSSHub 补；公共实例易限流，不依赖
　○ 事实性：AI 摘要只做归纳，保留原标题与原链接并标注"以原文为准"，避免模型幻觉被当成事实

■ 四　失败重试
　○ 错误分类
　　● 可重试：网络超时、连接重置、429、5xx → 指数退避加抖动（一秒／二秒／四秒，最多三次），尊重 Retry-After
　　● 不可重试：4xx 参数错误、token 失效、额度耗尽、消息超长 → 立即失败并告警，不做无意义重试
　○ 待补队列：推送失败的内容落盘，下一次运行合并补发，并在简报中注明"含补发内容"
　○ 通道 failover：企微 → Server酱 → 邮件／ntfy，任一成功即标记该条已送达
　○ 心跳监控：任务成功才向 Healthchecks.io 之类地址 ping 一次，超时未 ping 触发告警；告警通道必须与主通道分离，避免"被监控对象和告警走同一条坏掉的链路"
　○ 平台层重试：云函数可开异步调用重试与死信队列；GitHub Actions 的定时触发本身不自动重试，需在工作流内加重试步骤，或用外部 cron 在次日凌晨兜底触发一次 repository_dispatch
　○ 幂等是重试的前提：没有幂等键的盲目重试必然造成重复推送，两者必须一起实现


【拾】成本与分阶段落地

■ 成本
　○ 主选方案：零元。GitHub 公开仓库免费 Runner、企业微信机器人免费、Server酱 免费额度足够每日一条
　○ 可选成本：QQ 机器人免费；AI 摘要按 token 计费，每日一次用量极小；云函数即使超出免费额度也在每月几元内
　○ 隐性成本：免费额度政策变动、第三方推送服务停运、源站改版导致抓取规则失效 —— 用"多源 + 多通道 + 心跳告警"对冲

■ 分阶段
　一、最小可用：TrendRadar 模板 + GitHub Actions + 企业微信机器人，配好关键词，先跑通一条日报
　二、加固：引入幂等状态表、待补队列、心跳监控、源健康检查、第二推送通道
　三、个性化：接 AI 摘要、扩展个人关键词（城市／行业／机构／政策）、加 QQ 通道、加周报与月度回顾
　四、平台化（如需对外）：换成云函数 + 云数据库，补用户管理与订阅配置，并重新评估 GPL／AGPL 许可合规
